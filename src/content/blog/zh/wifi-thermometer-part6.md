> 上一篇单片机会睡了：STOP 模式 + 按键唤醒，电流从毫安跌到微安。但低功耗带来一个新恐惧：万一程序卡死了呢？醒着的时候卡死，你当场就能发现；睡着的时候卡死，设备就无声无息地耗电池，用户只会看到"它突然不更新了"。
> 本篇请出嵌入式界的保安队长：**独立看门狗 IWDG**。以及一条写在项目配置注释里的生死不等式。

---

## 一、本篇目标与效果

**目标**：给程序装上自动复活机制——故意让程序卡死，1.6 秒后它自动复位恢复运行，串口计数从零重来。

**做完你会懂**：看门狗的本质是一个"你不理我就拉你复位"的倒计时、它为什么必须用独立时钟、在哪喂狗是学问、以及为什么它的溢出周期**必须大于**睡眠周期。

## 二、原理 10 分钟

### 2.1 看门狗：不能辞职的倒计时

看门狗是一个递减计数器，倒数到 0 就触发系统复位。你的任务是在它数完之前不断"喂狗"（重装计数值）。程序跑得好好的，喂狗如呼吸；程序一旦卡死在某处没人喂狗，倒计时归零——**系统自动重启，从故障里自愈**。

IWDG（Independent Watchdog）的两个关键特征：

1. **独立时钟**。它吃的是芯片内部的低速 RC（STM32F103 是 LSI 约 40 kHz），不依赖主时钟系统。这一条在低功耗产品里是决定性的：**主时钟关掉的 STOP 模式里，IWDG 照样走**——它是唯一"你睡着它也醒着"的看门狗；
2. **启动后无法停止**。软件一旦开启 IWDG，直到复位前没有任何办法关掉它。这是防呆设计：出错的程序也"没资格"把狗关掉。副作用是——**开启之前必须把喂狗预算想清楚**，没有回头路。

（顺带一提还有 WWDG 窗口看门狗：它挂在主时钟上，STOP 里会停，且要求喂狗不能太早也不能太晚。低功耗产品用不上它，知道存在即可。）

### 2.2 超时时间怎么算

IWDG 的超时 = 预分频 × 重装载值 ÷ LSI 频率。F103 的预分频档位是 4/8/16/…/256，重装载值是 12 位数（最大 4095）：

```
超时 = (4 × 2^PR) × RLR / 40000
```

选一个 1.6 秒的示范配置：`PR = 6`（分频 256）× `RLR = 250` → 250×256/40000 = 1.6 s。

### 2.3 生死不等式：溢出周期 > 睡眠周期

这是本篇标题的由来，也是低功耗产品配置看门狗的铁律：

```
IWDG 溢出周期  >  一次完整睡眠 + 醒着干活的最坏时间
```

为什么？想想第 5 篇的睡眠：设备 STOP 10 秒，这 10 秒里主程序停在 `__WFI()`，**没人喂狗**（也喂不了）。如果你把看门狗配成 8 秒——设备每次睡着 10 秒，睡到第 8 秒就被狗咬醒……不是唤醒，是**复位**：SRAM 清空、计数清零、从头再来。设备会陷入"睡→咬→重启→睡→咬"的无限循环，永远干不成活。

我们的产品的数字：**睡眠 10 s，IWDG 溢出 16.384 s**。6 秒余量留给醒着采样、上报、协议处理的最坏情况。这条不等式后来直接写进了板级配置的注释里，原文是：

> 独立看门狗：溢出周期必须大于 Deepstop 睡眠周期（10 s），这里选 16.384 s

### 2.4 在哪喂狗，是一门哲学

喂狗位置的选择，本质是回答"**什么状态算程序健康**"：

- 喂在**主循环**：最常用。主循环转得动 = 程序活着；
- 喂在**中断里**：大忌。中断由硬件触发，哪怕主循环已经卡死在 `while(1)` 里，定时器中断照样进、照样喂狗——狗永远咬不下来，看门狗形同虚设；
- 喂在**每个状态入口**（产品的做法）：三状态机的每个 case 开头喂一次，粒度更细——哪怕状态机在某个状态里多转了几圈，只要还在转就活着。

反过来也成立：如果你发现某个耗时操作经常逼近喂狗周期，**不要简单地在中断里加喂狗**，那是掩耳盗铃。正确做法是重新算账：操作拆短、狗喂点优化，或者诚实地承认这个操作需要更长的超时。

## 三、动手写代码

### 实验一：基础看门狗——喂就活，不喂就咬

```c
#include "stm32f103xb.h"

static void iwdg_init_1s6(void)
{
    IWDG->KR  = 0x5555;              // 1. 解锁配置寄存器（不解锁不让写）
    IWDG->PR  = 6;                   // 2. 预分频 256
    IWDG->RLR = 250;                 // 3. 重装载 250 → 1.6 s
    while (IWDG->SR) { }             // 4. 等寄存器更新完成
    IWDG->KR  = 0xAAAA;              // 5. 先喂一口
    IWDG->KR  = 0xCCCC;              // 6. 启动！此后无法停止
}

static void iwdg_feed(void)
{
    IWDG->KR = 0xAAAA;               // 喂狗：重装 RLR
}
```

主循环：

```c
int main(void)
{
    /* …时钟、串口初始化… */
    iwdg_init_1s6();
    uart_puts("system up\r\n");

    while (1) {
        uart_puts("alive\r\n");
        delay_ms(500);
        iwdg_feed();                 // 主循环末尾喂狗
    }
}
```

运行正常后做对照实验：注释掉 `iwdg_feed()`，重新下载。现象：串口每 1.6 秒打一次 `system up`——系统在反复被咬复位。**亲眼看到这条狗咬人**，印象才算建立。

### 实验二：生死不等式现场演示

把超时改回 1.6 秒，然后让程序"睡"3 秒再喂狗：

```c
while (1) {
    uart_puts("alive\r\n");
    delay_ms(3000);                  // 模拟一次超时长的任务/睡眠
    iwdg_feed();                     // 3s > 1.6s，永远到不了这里
}
```

现象：`alive` 只打印一次，然后每 1.6 秒复位重启。这就是"溢出周期 < 干活周期"的下场。现在把超时改成 4 秒（`PR=6, RLR=625`），同样的 3 秒延时就能正常喂上了。

把这条迁移到产品语境：STOP 10 秒无人喂狗，超时就必须 > 10 s——**不等式不是建议，是配错即死的硬件级约束**。

### 实验三：自毁按钮——卡死自愈

最后来个完整的实用演示：按下按键，程序故意卡死，看门狗 1.6 秒后把它救回来。

```c
void EXTI0_IRQHandler(void)          // 按键中断里设置卡死标志
{
    if (EXTI->PR & EXTI_PR_PR0) {
        EXTI->PR = EXTI_PR_PR0;
        extern volatile int g_panic;
        g_panic = 1;
    }
}

volatile int g_panic = 0;

int main(void)
{
    /* …初始化… */
    iwdg_init_1s6();
    uint32_t n = 0;
    while (1) {
        if (g_panic) {
            uart_puts("I am stuck...\r\n");
            while (1) { }            // ★ 故意卡死：没人喂狗了
        }
        n++;
        uart_puts("tick\r\n");
        delay_ms(200);
        iwdg_feed();
    }
}
```

按下按键 → 打印 `I am stuck...` → 1.6 秒后串口重新出现 `system up`（如果你是复位后打印的话），**系统从卡死中自动复活**。这就是看门狗作为"最后一道防线"的标准工作画面。

## 五、原版对照（CIU32F003）

产品的 IWDG 配置在板级初始化里完成，超时宏集中定义：**16.384 秒**，对 10 秒 Deepstop 周期留 6 秒余量。喂狗点在主循环——而且是**三状态机的每个状态入口各喂一次**，不是循环尾部统一喂。

这个粒度选择背后有真实考量：产品的醒着阶段要跑 UART 协议处理、传感器采样、可能长达数秒的 Wi-Fi 交互（第 11 篇会展开）。如果统一在循环尾部喂狗，任何一个状态里多待了一会儿都可能逼近超时；放在每个状态入口，等于声明"**状态机还在转 = 系统健康**"——和业务语义对齐的喂狗点，比无脑循环尾部喂更经得起后期的功能膨胀。

另一个产品细节：看门狗在**上电后尽早**配置。原因很朴素——上电初始化本身也可能卡死（比如某个外设没响应），狗要尽早开始工作才能罩住这段。

## 六、彩蛋：狗是好狗，但它看不懂业务逻辑

开发中期，产品出过一个怪现象：设备一切正常——不卡死、不复位、看门狗喂得规规矩矩——但**每 10 秒醒来都会白给 Wi-Fi 模组上一次电**，电白白耗掉，数据却没上报。

排查发现：DP 缓存状态机里有一条路径，等待一个"握手完成"的标志，而这个标志在某些唤醒序列里永远不会被置位。于是状态机**忠诚地、永不停歇地**卡在那个等待循环里；主循环还在转、狗还在喂、系统从看门狗角度看无比健康——只是业务永远地停在了"等待"里。

修复方法今天看很简单：给等待加超时，超时后走兜底分支。但它留下一条比修复本身更重要的教训：

> **看门狗保证的是"程序在转"，不保证"业务在前进"。** 喂狗点正确，只解决了系统健壮性的一半；另一半是每个"无限等待"都必须自带超时兜底——等待握手要有等待超时，等待传感器要有 NACK 重试上限，等 Wi-Fi 连网要有窗口上限。**一切等待都必须可超时**，这是和"喂狗位置"平级的第二条纪律。

后来这条纪律也体现在睡眠窗口设计上（第 7 篇会看到）：整个醒着阶段被包在一个最长 10 秒的窗口里，窗口一到强制入睡——即使 Wi-Fi 还没连上。不给任何"等待"无限期的特权。
