## 一、案发：设置总是"神秘复原"

测试同事报障，原话是这样的：

> "我在 App 上把高温告警阈值改成 35 度，当时是好的。过了几个小时再看，**又变回默认的 30 度了**。改了好几次都这样。"

稳定复现，不是偶发。这是嵌入式界最恐怖的 bug 类型之一：**它有明确的业务症状（设置丢失），但没有程序症状（不死机、不报错、不复位）**。

立案。先记录现场勘查能确认的事实：

- 丢失的是**存在 Flash 里的用户设置**（温度/湿度阈值、校准值等）；
- 丢失后的值恰好是**出厂默认值**——不是随机数，不是清零，是默认值；
- 代码里会"把设置恢复成默认值"的地方只有一个：**恢复出厂流程**。

也就是说，"设置丢失"的真相是"设备执行了一次恢复出厂"。那么问题来了：是谁、在什么时候、为什么触发了它？

## 二、第一嫌疑人：Flash 存储没写好

最直觉的怀疑：存储代码有 bug，没写进去，上电读到的是 Flash 里的出厂镜像。

验证方法很简单：在存储模块加日志，写入后立即读回校验。**结果：写入成功，读回一致。** 而且有个反证很有力——如果是"没存住"，那默认值应该是**上电时**出现的；但实测丢失往往发生在**设备运行了一段时间之后**，甚至发生在白天好好的、晚上就变了的场景里。

存储代码的嫌疑排除。但它给了一个关键线索：**默认值是"恢复出厂流程"主动写进去的**，这条线索后面用得上。

## 三、第二嫌疑人：云端下发了默认值

第二直觉：是不是云端把旧配置同步下来了？低功耗协议里有 DP 缓存机制——设备连上云后，会从云端拉一份缓存应用下来。如果云端缓存里存的是旧值，设备"应用缓存"就等于把用户的设置覆盖了。

验证：串口抓帧，盯 DP 下发方向。**没有**。缓存应用的日志也显示拉到的值就是用户最新设的。云端嫌疑排除。

注意，到这一步我们已经在错误的方向上花了半天。复盘这半天的浪费：**两个嫌疑人都很合理，但都只是"合理"，没有任何一个假设被"抓帧"验证过**。这是本案的第一个教训，先记账，结尾再总结。

## 四、转折点：给故障画一条时间线

换思路。不再猜"谁干的"，改为对齐"**什么时候干的**"。在恢复出厂流程的入口打上日志（一行 printf），同时记录每次 Wi-Fi 模组上电的时刻，让设备自己招供。

日志一出来，案子就破了一半：

```
[12:03:14] wifi power on          ← Wi-Fi 模组上电
[12:03:15] FACTORY RESET!!!       ← 恢复出厂被触发
[12:03:15] 默认值写入 Flash
```

**每次恢复出厂，都发生在 Wi-Fi 模组上电后的 1 秒内。** 不是"过几个小时随机发生"——低功耗设备大多数时间在睡觉，模组断电；用户每次在 App 上操作会唤醒设备上报，模组重新上电——上电即恢复出厂。几个小时才复现一次，只是因为"用户在 App 上操作"几个小时才发生一次。

时间线对齐法是嵌入式排障的瑞士军刀：**给每个可疑事件打时间戳，让相关性自己浮出来。**

## 五、真凶现形：重看那条 7 字节空帧

凶手必定藏在这 1 秒的窗口里。这个窗口里模组会干什么？翻协议文档 + 串口抓帧，模组上电的第一句话就是第 8 篇我们解剖过的那条：

```
55 AA 00 02 00 00 01
```

当时留了个扣子：按校验和规则它该是 `0x02`，帧里却是 `0x01`。现在把这条帧的解剖图重新挂出来，四个巧合摆在一起看：

```
字节:  55   AA   00    02    00   00    01
        │    │    │     │     │    │     │
      帧头  帧头  版本  命令字  长度=0  无数据 校验和
                                  │           │
                                  └── 巧合①：这是一条【空数据帧】
                                              │
                              巧合②：SDK 解析 0x02 时【不看长度】
                                       直接读"数据区第 1 字节"
                                       ──读到的就是 0x01
                                              │
                              巧合③：涂鸦协议里 0x01 恰好是
                                       【AP 配网状态】的编号
                                              │
                              巧合④：应用层收到"进入配网状态"
                                       的约定动作是【恢复出厂】
```

四个巧合单独看都人畜无害，串成一条链就是事故：**模组发空帧问好 → SDK 把校验和当数据读 → 0x01 被翻译成"AP 配网" → 恢复出厂擦掉了用户的设置。**

看 SDK 源码，问题代码长这样（简化示意）：

```c
case 0x02:                              /* 工作模式/状态处理 */
    state = received_data[0];           /* ★ 无长度检查，空帧时读到的是校验和 */
    if (state == AP_STATE) {
        mcu_reset_wifi();               /* 进而触发恢复出厂…… */
    }
    break;
```

修复也只有一行——**用之前先问长度**：

```c
case 0x02:
    if (data_len >= 1) {                /* 空数据帧不许碰数据区 */
        state = received_data[0];
        ...
    }
    break;
```

## 六、动手：亲手复现并修复这个 bug

光听故事不过瘾，我们在学习版上把这个案子重演一遍。

**第一步：写一个"带病的"迷你状态处理器**（就是第 8 篇解析器的业务层，加个故意的 bug）：

```c
static void on_frame_ready(rx_t *f)
{
    switch (f->cmd) {
    case 0x02: {
        /* 病句：不看 f 里记录的数据长度，直接读 data[0] */
        uint8_t state = f->data[0];        // 空帧时，解析器把校验和放进了这里
        if (state == 0x01) {
            uart_puts("!!! factory reset triggered\r\n");
        }
        break;
    }
    ...
    }
}
```

**第二步：串口助手发送 `55 AA 00 02 00 00 01`**——串口立刻打印 `!!! factory reset triggered`。案子复现。

**第三步：修复**。在 `on_frame_ready` 入口加长度检查（`len = (lenh<<8)|lenl; if (len < 1) break;`），再发同一条帧——安静了，无任何动作。

十分钟的实验，体验一遍真实案件数月排查的核心冲突：**读数据之前，先确认数据存在。** 这条纪律扩展一下，就是所有解析器代码的第一准则：**永远不要相信输入的长度声明之外，还有隐含的数据。**

## 七、结案的最后一课：SDK 是"借来的代码"

案子破了，但有个尾巴必须处理：**这行修复是在 SDK 源码里动的**。

SDK 是第三方代码，将来会升级。升级时如果直接覆盖 `system.c`，这个修复就悄无声息地丢了——bug 回归，而且没有任何编译错误提醒你。所以项目养成了习惯，维护一份"**SDK 修改清单**"，每次升级对着清单逐项确认：

| 修改 | 位置 | 原因 |
|------|------|------|
| 0x02 空帧长度校验 | 解析层 | 本案：空帧校验和被误读为 AP 状态 |
| （缓冲区宏顺序修复） | 移植配置头 | 第 9 篇彩蛋：多 DP 下发静默被拒 |
| （产测命令字兼容） | 命令分发 | 第 17 篇展开 |

借来的每一行代码，都要记在自己账上。

## 八、方法论总结：这场案子的四件遗物

回看整场排查，最值得带走的不是那一行修复，是四条方法论：

**① 时间线对齐法。** 别猜"谁干的"，打时间戳对齐"什么时候干的"。相关性自己会浮出来。一行日志胜过一天猜测。

**② 抓帧优先于理论化。** 本案浪费的半天，都花在"猜—验证—排除"的循环里。正确姿势是**第一步就抓帧**：串口/逻辑分析仪先把事实钉死，再动脑子。嵌入式调试的直觉在协议层经常失效，因为协议 bug 全是静默的。

**③ 每个巧合都要问为什么。** 校验和为什么恰好是 0x01？因为这条帧是空的，0x01 是累加的必然结果，而 0x01 恰好有语义。工程世界里没有"巧合"，只有"你还没读懂的必然"。

**④ 静默失败最贵，日志就是监控。** 恢复出厂这种高危操作，入口必须有日志。写代码时多问自己一句："这条路走了，谁看得见？"——第 9 篇彩蛋的结语，在这里又说了一遍。值得说两遍。

## 九、原版对照（CIU32F003）

产品在低功耗模组上完整经历了本案：每次 Wi-Fi 上电，模组发空数据区的 0x02 查询，SDK 原版实现无条件读数据字节，把恒为 0x01 的校验和当成 AP 配网态，**每次上电误触发恢复出厂**——擦 Flash、写默认值，表现为"设置存了但下次上报又是旧值"。修复方案与本篇实验一致：解析处加数据区长度校验。

这个修复是产品的 SDK 修改清单上的第一条，也是"升级 SDK 时必须保留"的头号条目。排查过程中走过的弯路（先查存储、再查云端）也原样记录在案——**团队文档里保留弯路，是为了让下一个人不再走**。
