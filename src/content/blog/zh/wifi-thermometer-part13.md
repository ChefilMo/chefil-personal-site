## 一、本篇目标与效果

**目标**：学习版驱动 1602 屏，把温湿度显示上去，并挂进第 7 篇的主循环——每次醒来采样后刷新屏幕。

## 二、原理 10 分钟

### 2.1 段码屏 vs 字符屏：产品选了什么、为什么

LCD 屏分两大门派：

**段码屏（Segment LCD）**：屏上的每个笔画段是一个独立电极（"8"字由 7 段组成，外加温度符号、电池图标等定制段），驱动芯片（产品用 VKL076）负责产生液晶需要的交流驱动波形。MCU 的职责被压缩到极简：**通过 I2C 往显存里写位图**，哪段该亮就把显存里对应的 bit 置 1，驱动芯片自动把显存翻译成屏幕上的段。

**字符屏（1602）**：屏内带点阵字库，你发字符码它显示字符。学习版的 1602 还加了一层：屏背后是 HD44780 控制器，I2C 转接板（PCF8574）只是把一个 8 位并口"折叠"成了 I2C 接口——每次 I2C 写，本质是模拟一次并口操作。

产品选段码屏的理由很产品：**功耗**。段码屏驱动电流以微安计，而且产品要的 UI 极简单（几个数字+几个图标），段码屏的"图标即段"天生契合；1602 那点阵屏的背光，光背光就够吃掉这个产品的电池预算。

### 2.2 显存模型：一切 LCD 驱动的共同语言

不管段码还是点阵，驱动芯片的核心抽象都是**显存（VRAM）**：一块和屏幕物理结构一一对应的内存。你的全部工作就两件事：

1. 初始化芯片（告诉它屏的参数、点亮驱动）；
2. 改显存里的 bit，让屏幕变化。

产品里"LCD 显示"的分层因此非常干净：上层说"显示 25.3℃"，下层把这个数字查"段码表"（每个数字由哪几段组成）翻译成 bit，写进显存。**业务代码永远不和显存打交道**——这层隔离让第 14 篇的按键、第 7 篇的状态机都能直接调 `app_display_show_value()` 而不关心屏幕细节。

### 2.3 液晶的怪癖：交流驱动

顺带说一个段码屏特有的冷知识：**液晶不能加直流电压**，直流会让液晶材料电解老化。所以驱动芯片输出的是不断翻转极性的交流波形（这也解释了为什么屏上的段明明"恒亮"，电极上其实一直在交替正负）。这个知识平时用不上，但当你看到驱动芯片有一堆 bias/boost 配置项时，就知道它们在伺候这个物理特性。

## 三、动手写代码（学习版：1602 @ 模拟 I2C）

### 第一步：接线与协议认识

1602 模块 4 根线：VCC、GND、SDA→PB7、SCL→PB6——和第 3 篇的 GXHT40 共用同一条模拟 I2C 总线！这就是总线协议的好处：一条线上可以挂多个器件（地址不同互不干扰）。模块地址通常是 `0x27`（也有 `0x3F`，背面有焊盘可以改）。

PCF8574 转接板的 8 位并口含义：

```
bit0=RS  bit1=RW  bit2=EN  bit3=背光  bit4~7=数据高4位(HD44780走4位模式)
```

RS=0 是命令、RS=1 是数据；EN 需要一个"高脉冲"锁存（和 I2C 的 ACK 无关，是 HD44780 的并口时序遗风）。

### 第二步：驱动代码

```c
#define LCD_ADDR    0x27
#define LCD_BL      0x08
#define LCD_EN      0x04
#define LCD_RS      0x01

static void lcd_pulse(uint8_t val)          // EN 高脉冲锁存
{
    i2c_start();
    i2c_write_byte((LCD_ADDR << 1) | 0);    // 地址+写（第 3 篇的函数原样用）
    i2c_write_byte(val | LCD_EN | LCD_BL);
    i2c_stop();
    i2c_start();
    i2c_write_byte((LCD_ADDR << 1) | 0);
    i2c_write_byte(val | LCD_BL);           // EN 拉低
    i2c_stop();
    delay_ms(1);
}

static void lcd_write_nibbles(uint8_t data, uint8_t rs)
{
    lcd_pulse((data & 0xF0) | rs);          // 高 4 位
    lcd_pulse((data << 4) | rs);            // 低 4 位
}

static void lcd_cmd(uint8_t c)  { lcd_write_nibbles(c, 0); }
static void lcd_data(uint8_t d) { lcd_write_nibbles(d, 1); }

static void lcd_init(void)
{
    delay_ms(50);
    lcd_pulse(0x30); delay_ms(5);           // HD44780 规定的上电唤醒序列
    lcd_pulse(0x30); delay_ms(5);           // （4位模式下也要先发 3 次 8 位命令，
    lcd_pulse(0x30); delay_ms(1);           //  别问为什么，datasheet 就这么写）
    lcd_pulse(0x20); delay_ms(1);           // 切 4 位模式
    lcd_cmd(0x28);                          // 2行×16列，4位数据
    lcd_cmd(0x0C);                          // 显示开，光标关
    lcd_cmd(0x06);                          // 写入后光标右移
    lcd_cmd(0x01);  delay_ms(2);            // 清屏
}

static void lcd_set_cursor(uint8_t row, uint8_t col)
{
    lcd_cmd(0x80 | (row ? 0x40 : 0) | col);
}

static void lcd_print(const char *s)
{
    while (*s) lcd_data(*s++);
}
```

### 第三步：挂进主循环

在第 7 篇的 WAKEUP 状态里，`app_do_measurement()` 之后加：

```c
char line[17];
/* 第一行：温度 */
lcd_set_cursor(0, 0);
sprintf-like 手工填充 → "T:25.3C   ";
lcd_print(line);
/* 第二行：湿度 + 电量 */
lcd_set_cursor(1, 0);
lcd_print(line2);   // "H:52% BAT:80%"
```

1602 没有 ℃ 符号就写 "C"（产品有定制的 ℃ 段，段码屏的定制图标优势就在这里）。刷新频率跟着 LPTIM 周期走——10 秒一次，人眼完全够用，这是第 7 篇就定下的节奏。

## 四、烧录与验收

- [ ] 上电后第一行显示温度、第二行显示湿度+模拟电量，数值和串口打印一致；
- [ ] 对着传感器哈气，10 秒内屏幕湿度更新（跟着唤醒周期走）；
- [ ] 逻辑分析仪抓 LCD 的 I2C 帧：能看到 `0x27<<1` 的地址字节和 GXHT40 的 `0x88` 在同一条总线上交替出现——**一条总线两个从机**，第 3 篇埋的"总线"概念完全兑现；
- [ ] （排障演练）屏全黑/全白无任何字符：八成是地址不对（`0x27` 换成 `0x3F` 试试），用第 3 篇的 ACK 检测法扫描总线就能确认哪个地址有应答。

## 五、原版对照（CIU32F003 + VKL076）

产品驱动 VKL076 段码屏，本篇的两个能力都有对应，形态不同：

1. **第二路独立模拟 I2C**。LCD 走 PA1/PA0，与传感器的 PB3/PB4 完全分开——两路总线互不拖累，LCD 初始化期间传感器照常可用。**模拟 I2C 最大的好处在此兑现：要几路有几路，纯软件复制**；
2. **显存 = 段映射表**。VKL076 的显存每个 bit 对应屏上的一个物理段。产品的显示模块维护一张"段码表"：数字 0~9 各自由哪几段组成、℃ 符号占哪几位、Wi-Fi 信号几格各占哪几位——应用层报数字，底层查表写位；
3. **温标切换是"换一张表"**。用户 App 上把 ℃ 切到 ℉，显示层换算数值后，小数点段和 ℉ 段的显存位一起改——上层一个标志，底层一次查表；
4. **图标是产品体验的大头**。电量低于 20% 点亮低电图标段、Wi-Fi 状态格、告警铃铛……这些"小事"构成了用户对品质的全部体感。段码屏让每个图标都是一段免费的"像素"；
5. **进 Deepstop 前安排 standby**。屏幕驱动芯片有低功耗 standby 模式：进 Deepstop 前让 VKL076 睡下（显存保持、驱动停振），醒来再唤醒——屏幕内容在睡眠期间保持显示，功耗却降了一截。这是"睡觉前检查清单"（第 5 篇）之外的又一条目。

## 六、彩蛋：那个写进配置的占位符，终于修正了

还记得第 2 篇框架落地时的配置吗？LCD 地址写的是：

```c
#define VKL076_ADDR    0x3C    /* 占位：拿到 VKL076 datasheet 后修正 */
```

当时datasheet没到手，老实写"占位"，没瞎编。后来拿到文档一对——**真实地址是 0x3E**。差两个 bit，后果就是 I2C 上永远 NACK，屏一辈子初始化不成功。

这个伏笔现在可以讲透了，因为它背后是一条移植方法论：**驱动芯片的四个"想当然"杀手**——地址想当然、初始化序列想当然、显存映射想当然、电气参数想当然。每一个的排查成本都是从"半天"起步的：地址错，总线沉默；初始化序列错，屏全白或全黑；显存映射错，数字显示成缺笔画的鬼画符（段码表的段序和实际屏不一致时，你甚至能"显示"出字典里不存在的符号）。

所以移植一颗陌生驱动芯片的纪律是：**datasheet 的每一个数字都是第一手资料，参考驱动是第二手，你的记忆一文不值**。初始化序列逐条对照文档，显存映射拿"全显测试"验证（让所有段全亮一遍，肉眼对实物），地址用 ACK 扫描确认。这三板斧走完，剩下的才是写业务代码。

产品在产测里还专门保留了这个动作：产测模式下短按按键，屏幕**全显全部笔画 5 秒**，产线目检有没有缺段——显存映射的验证从开发期一直延续到产线（第 17 篇产测篇展开）。
