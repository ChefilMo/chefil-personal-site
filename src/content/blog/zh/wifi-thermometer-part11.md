> 协议会跑了、SDK 会转了、大案也破了。现在到了低功耗产品独有的难题：**设备每次醒来，云端和本地谁的数据新？**
> 用户在 App 上刚把温度上限改成 35℃，设备此刻正在 Deepstop 里睡得香；它醒来连云之后，是先问云端"有什么新设置"、还是先把本地数据报上去？顺序错了，旧值覆盖新值，用户白改。
> 本篇解决这个时序之争，顺便实现全系列最大的一个设计：**14 个 DP 合单帧上报**。

---

## 一、本篇目标与效果

**目标**：实现一个简化版 DP 缓存状态机，完成"醒来 → 连云 → 拉缓存 → 应用缓存 → 单帧全量上报"的完整链路，并用串口助手扮演模组+云端跑通两种结局：

1. 云端有缓存（用户改过的设置）——设备应用后再上报，面板不"回跳"；
2. 云端没缓存——2 秒超时兜底，照常上报。

**做完你会懂**：DP 的本质、离线缓存为什么存在、缓存与上报的时序为什么必须是"先拉后报"、以及单帧上报的工程理由。

## 二、原理 10 分钟

### 2.1 DP：设备与云对话的"词汇表"

DP（Data Point，数据点）是涂鸦协议的核心抽象：**设备所有可上报、可控制的状态，都是一个个编号的 DP**。本产品的词汇表节选：

| DPID | 名称 | 方向 | 类型 |
|------|------|------|------|
| 1 | 温度 | 上报 | 数值 |
| 2 | 湿度 | 上报 | 数值 |
| 3 | 电池电量 | 上报 | 数值 |
| 5 | 外部温度 | 上报 | 数值 |
| 101~104 | 温度/湿度上下限 | **双向** | 数值 |
| 105 | 高温告警 | 上报 | 枚举 |
| 108 | 温标切换（℃/℉） | **双向** | 布尔 |
| 111 | 告警静音 | **双向** | 布尔 |

上报走 **0x07** 帧（MCU → 模组 → 云），下发走 **0x06** 帧（云 → 模组 → MCU，进 `dp_download_handle` 回调）。14 个 DP 里双向的那几个，就是"用户能改、设备要存"的设置类 DP——也是本篇的主角。

### 2.2 离线缓存：为睡眠而生的机制

低功耗设备 99.5% 的时间在 Deepstop，Wi-Fi 断电、和云彻底断联。问题来了：用户此刻在 App 上改温度上限，改的是**云端的数据**。设备完全不知情，它本地内存里还是旧值。

如果设备不管三七二十一醒来就上报本地旧值，云端会把旧值当成设备的最新状态同步给面板——**用户在 App 上刚改完，面板一闪又跳回旧值**。体验灾难。

涂鸦的解法是 `DO_CACHE_SUPPORT`（第 9 篇裁剪表里"必留"的那项）：设备连云后，可以发 **0x90** 命令向模组请求"离线期间攒下的缓存"——本质是模组替设备暂存了云端下发。模组从云端取回缓存，设备把缓存里的新值**应用**到本地，然后再上报。顺序铁律：

```
先拉缓存并应用 → 再全量上报
```

### 2.3 缓存状态机：三个出口，一条底线

完整链路的状态机：

```
        Wi-Fi 上电
            │
            ▼
   ┌── WAIT_ONLINE ──握手完成且连云──▶ CACHE_REQUESTED ──收到缓存──▶ 应用缓存 ──┐
   │      （等模组就绪）                     │  2s 超时                       │
   │                                       ▼                                ▼
   │                                  超时兜底                          REPORT（单帧全量上报）
   └────────────────────────────────────────────────────────────────────────┘
                                   上报完成 → 更新上报基准 → 本周期收工
```

三个出口（收到缓存 / 超时 / 兜底），**全量上报只有这一个触发点**——这条纪律叫"上报唯一出口"。它杜绝了散落的十处 `report_something()` 互相打架：任何时候你想知道"这次醒来到底报没报、什么时候报"，答案只有一处可查。

两个精心选择的参数，背后是实测数据：

- **缓存超时 2 秒**：模组收到 0x90 后要去云端拉数据，实测回包 **0.9~1.4 秒**。早期设过 500 ms——缓存还在路上就误判"没缓存"，本该应用的设置被跳过。超时不是拍脑袋，是按最慢实测值留余量；
- **上报基准**：全量上报完成后，把 14 个 DP 的当前值记为基准。之后每次醒来（第 7 篇）拿当前值和基准比：变化够大才触发下一个上报周期。基准在这里更新，判定才有意义。

### 2.4 为什么 14 个 DP 要合单帧

SDK 的常规用法是逐 DP 调用上报 API——每个 DP 一帧，连发 14 帧。问题出在物理层：9600 波特率下 14 帧连发要一百多毫秒，期间任何一次 Wi-Fi 波动、任何一帧丢失，**模组收到的就是残缺的一组 DP**。面板上的表现：温度更新了、湿度没更新，电池还是旧值——"数据不全"的客诉就是这么来的。

产品的解法：**自己组一帧大的 0x07**，把 14 个 DP 按协议编码规则顺次塞进数据区，一次发出。发送缓冲为此开到 128 字节（被最大帧决定，第 9 篇记过账）。单帧要么完整到达、要么整体重试，不存在"半截状态"。

## 三、动手写代码

### 第一步：DP 缓存与单帧组包

```c
typedef struct {
    int16_t  temp_x10, hum_x10, ext_temp_x10;
    uint8_t  battery;
    uint16_t temp_hi, temp_lo, hum_hi, hum_lo;
    uint8_t  unit_f;         // 0=℃, 1=℉
    uint8_t  mute;
    /* …共 14 项，双向 DP 也在其中… */
} dp_cache_t;

static dp_cache_t s_dp;               // 当前值（应用层维护）
static dp_cache_t s_report_ref;       // 上次上报基准

/* 单帧全量上报：手搓 0x07 大帧 */
static void report_all_single_frame(void)
{
    uint8_t buf[128];
    uint16_t n = 0;

    buf[n++] = 0x55; buf[n++] = 0xAA;
    buf[n++] = 0x03;                    // 版本
    buf[n++] = 0x07;                    // DP 上报命令字
    /* 数据区从 buf[7] 开始，先留 2 字节长度，填完回填 */
    uint16_t dstart = n + 2;

    n = dstart;
    buf[n++] = 1;  buf[n++] = 0x02;     // DPID=1 温度, 类型=数值(2字节)
    buf[n++] = (uint8_t)(s_dp.temp_x10 >> 8);
    buf[n++] = (uint8_t)(s_dp.temp_x10 & 0xFF);
    buf[n++] = 2;  buf[n++] = 0x02;
    buf[n++] = (uint8_t)(s_dp.hum_x10 >> 8);
    buf[n++] = (uint8_t)(s_dp.hum_x10 & 0xFF);
    /* …其余 12 个 DP 同法追加… */

    uint16_t dlen = n - dstart;
    buf[5] = (uint8_t)(dlen >> 8);
    buf[6] = (uint8_t)(dlen & 0xFF);

    uint8_t sum = 0;
    for (uint16_t i = 2; i < n; i++) sum += buf[i];
    buf[n++] = sum;

    for (uint16_t i = 0; i < n; i++) uart_putc(buf[i]);   // 单帧一次发出

    s_report_ref = s_dp;                // 更新上报基准
}
```

每个 DP 的编码是三元组：`DPID + 类型/长度 + 数据`，与 SDK 逐字节编码规则完全一致——**所以这一帧和逐 DP 上报在协议层完全等价，只是合并了传输次数**。

### 第二步：缓存状态机

```c
typedef enum {
    CS_IDLE = 0,            // 本周期未开始
    CS_WAIT_ONLINE,         // 等握手 + 连云
    CS_CACHE_REQUESTED,     // 已发 0x90，等缓存或超时
    CS_REPORT,              // 缓存处理完（三出口汇合），执行全量上报
    CS_DONE                 // 本周期结束，等待下一个 Wi-Fi 上电周期
} cache_state_t;

static cache_state_t s_cs = CS_IDLE;
static uint16_t s_cs_tick = 0;
static bool s_online = false;           // 由"收到模组联网状态帧"置位

void cache_task_10ms(void)              // 挂在第 7 篇 PROCESS 状态的 tick 上
{
    switch (s_cs) {
    case CS_IDLE:
        if (wifi_power_is_on()) {       // Wi-Fi 上电周期开始
            s_cs = CS_WAIT_ONLINE;
            s_cs_tick = 0;
        }
        break;
    case CS_WAIT_ONLINE:
        if (s_online) {                 // 握手完成且连云
            tuya_send_frame(0x03, 0x90, NULL, 0);   // 请求离线缓存
            s_cs = CS_CACHE_REQUESTED;
            s_cs_tick = 0;
        } else if (++s_cs_tick >= 1000) {           // 10ms tick × 1000 = 10s
            s_cs = CS_DONE;             // 连云失败：本周期放弃，不白等
        }
        break;
    case CS_CACHE_REQUESTED:
        if (cache_received_and_apply()) {           // 出口①：缓存到达
            s_cs = CS_REPORT;
        } else if (++s_cs_tick >= 200) {            // 出口②：2s 超时
            s_cs = CS_REPORT;           // 超时兜底，照常上报
        }
        break;
    case CS_REPORT:
        report_all_single_frame();      // 出口③：全量上报唯一出口
        s_cs = CS_DONE;
        break;
    case CS_DONE:
        break;
    }
}
```

## 四、烧录与验收：对手戏第三季（脚本化演出）

串口助手继续扮演模组，这次还要扮演云端。按剧本走：

- [ ] **第一幕（有缓存）**：助手依次发——心跳→工作模式查询→**联网状态帧**（`s_online` 置位）→ 收到单片机自动发出的 `55 AA 03 90 00 00 93`（0x90 请求，亲手验算校验和）→ 助手回一条含 DP101=35 的缓存帧 → 单片机应用（串口打印"cache applied: temp_hi=35"）→ 单片机**发一个 0x07 大帧**（逻辑分析仪可见全部 14 个 DP 首尾完整）；
- [ ] **第二幕（无缓存）**：重来，0x90 之后助手装死不回。2 秒后（±10ms 精度）单片机照常发出全量上报帧——**超时兜底生效**；
- [ ] **第三幕（连云失败）**：助手不发联网状态帧。10 秒窗口内单片机始终不发 0x90、不报错、窗口结束正常入睡——**放弃要安静，失败要有界**；
- [ ] **第四幕（顺序验证）**：对比第一幕中"应用缓存"日志的时间戳和 0x07 帧的时间戳——**应用在前，上报在后**，顺序铁律肉眼可证。

## 五、原版对照（CIU32F003）

学习版的骨架是产品逻辑的忠实缩影，产品上有四个更深的产品化细节：

1. **0x90 只发一次、且必在连云之后**。模组没连云时发 0x90 会被无视，所以状态机严格等"握手完成 + 联网状态确认"双条件；
2. **模组 0x08 查询（"把你所有 DP 报一遍"）是空实现**——不回复。因为全量上报唯一出口在缓存状态机手里，0x08 若直接触发上报，就可能发生在缓存应用**之前**，旧值覆盖用户新设置（2.2 节那个灾难）；
3. **Wi-Fi 断电期间，联网状态置为"未知"占位**。模组断电后它的联网状态已无意义，应用层显式置 0xFF 防止 LCD 按旧状态瞎显示图标；
4. **配网完成后的首次上报也走同一条链路**。不因为它"特殊"就开第二条路——唯一出口纪律对首次上电、配网完成、普通唤醒一视同仁。

## 六、彩蛋：三次与缓存的交锋

缓存状态机是项目里返工次数最多的模块之一，三次真实交锋简录如下：

**交锋一：命令字写错。** 请求缓存最初用的命令字与标准文档对不上——模组根本不认识，永远不回复，状态机每次都走超时兜底。表象"功能正常"（确实能上报），实际缓存从未生效过，用户设置偶发被旧值顶掉。教训：**涉及协议命令字，逐一对照官方文档原文，别信记忆**（这个 bug 直到专门 review 协议文档才暴露）。

**交锋二：500 ms 超时误杀。** 超时初值设 500 ms，觉得"绰绰有余"。实测模组去云端取缓存要 0.9~1.4 秒——缓存帧稳定地死在超时线上，状态机永远走兜底分支，和交锋一殊途同归。**"感觉够用"是嵌入式里最不可靠的度量，示波器和日志才是**。

**交锋三：连发丢帧逼出合单帧。** 逐 DP 上报在实验室里永远成功——信号好、距离近、模组清醒。直到某次完整回归测试出现"面板数据偶尔缺一项"，才意识到 14 帧连发在真实链路下的丢失率。合单帧之后，"数据不全"的客诉类型彻底消失。

三次交锋的共同主题：**实验室里能跑，只是 bug 还没等到它的天气。** 每修一次，就把"实测最慢值、最坏链路、真实环境"这三个词在团队里的权重调高一点。

## 七、下篇预告

缓存能应用了，但还有个漏洞：用户改的设置目前只存在 RAM 里——设备一Deepstop…不，RAM 倒是不丢，可一旦**复位**（换电池、看门狗、OTA），设置全没。下一篇第 12 篇《Flash 持久化》：内部 Flash 的擦写规则（先擦后写、按页擦除）、为什么"每个设置各存一份"会把 Flash 磨穿、以及产品的统一存储块设计。
