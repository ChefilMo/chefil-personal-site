> 第 8 篇我们手写了协议解析，教学价值拉满，但产品里不会真的手写下去——涂鸦官方提供 MCU SDK，组帧、解析、DP 管理都封装好了。
> 本篇做移植。移植 SDK 听着是体力活，真正的工作只有一个字：**算**。在 3 KB RAM 的芯片上移植 SDK，第一件事不是编译，是拿出预算表，决定哪些功能活、哪些功能死。

---

## 一、本篇目标与效果

**目标**：把涂鸦低功耗 MCU SDK 移植到单片机上——接上四个对接点、配好产品信息、按预算裁剪功能。移植完成后，第 8 篇手写的"回复心跳/工作模式查询"由 SDK 自动完成，串口助手扮演模组再演一遍对手戏，全程零手写协议代码。

**做完你会懂**：SDK 的三个源文件各管什么、移植的本质是填四个"插槽"、以及小资源芯片上做移植的裁剪决策方法。

## 二、原理 10 分钟

### 2.1 SDK 的三个文件，三种身份

涂鸦低功耗 MCU SDK 核心就三个 .c 文件，职责清晰：

| 文件 | 身份 | 干什么 |
|------|------|--------|
| `system.c` | **协议引擎** | 帧解析状态机（就是第 8 篇我们手写的那个，工业级加强版）、命令分发、数据缓存 |
| `protocol.c` | **产品字典** | 你这个产品的 DP 定义表（DPID、类型、长度）、上下行数据处理函数 |
| `mcu_api.c` | **用户 API** | 给应用层调用的接口：`mcu_dp_value_update()`（上报）、DP 下载回调等 |

移植要做的，就是让这三件套在你的硬件上转起来——**SDK 是现成的机器，我们给它接上电、喂上料、接上产品图纸**。

### 2.2 四个对接点：SDK 和世界的四个插槽

SDK 通过四个明确的"插槽"和外界交互，全部是我们前几篇亲手写过的能力：

**① 发送字节**——`uart_transmit_output(unsigned char value)`：

```c
void uart_transmit_output(unsigned char value)
{
    uart_putc(value);          // 第 2 篇的阻塞发送
}
```

**② 接收字节**——`uart_receive_input(unsigned char value)`：不用你实现，是 SDK 提供的函数，你在**串口中断**里调用它：

```c
void USART1_IRQHandler(void)
{
    if (USART1->SR & USART_SR_RXNE) {
        uart_receive_input((uint8_t)USART1->DR);   // 每字节直接喂给 SDK
    }
}
```

注意到没有？第 8 篇我们自己写的环形缓冲和解析状态机，SDK 版本里**接收端不再需要我们的缓冲**——SDK 内部有自己的协议缓冲区，字节进去就直接进了解析流水线。我们的环形缓冲光荣退休。

**③ 主循环驱动**——`wifi_uart_service()`：在 10 ms tick 里调用（第 7 篇 PROCESS 状态的 `uart_service_tick()` 就是它的位置）。SDK 的解析、超时判断、缓存状态机全靠这个节拍推进。

**④ 业务回调**——`dp_download_handle()`：模组下发 DP（比如用户在 App 改了温度上限）时 SDK 会调到这个函数，你在里面把指令翻译成对应用变量的修改：

```c
void dp_download_handle(unsigned char dpid, const unsigned char value[], unsigned short len)
{
    switch (dpid) {
    case 1:   /* 温度上限 */
        /* 从 value[] 解出数值，写进自己的变量，最好存 Flash（第 12 篇）*/
        break;
    default:
        break;
    }
}
```

四个插槽接完，机器就能转了。剩下的全是配置。

### 2.3 产品信息：报户口

`protocol.c` 开头有一组宏，相当于设备在涂鸦平台的"户口本"：

```c
#define PRODUCT_KEY     "你的ProductKey"   // 涂鸦开发者平台上创建产品后获得
#define MCU_VER         "1.0.0"            // MCU 固件版本，OTA 用（第 16 篇）
```

还有低功耗产品特有的"能力声明"：支持 Wi-Fi 电源控制（MCU 决定模组何时断电）、支持离线缓存……这些标志告诉模组"对面是个懂低功耗规矩的 MCU"，模组会按低功耗节奏配合。

## 三、动手：先算账，再编译

### 第一步：拿 SDK 与建账

在涂鸦开发者平台（iot.tuya.com）注册、创建产品（品类选"温湿度传感器"），平台会生成包含 `mcu_sdk` 的 SDK 包下载下来。把三个 .c 扔进工程。

**编译之前，先打开 Keil 的 .map 文件，把移植前的账记下**（工程选项"Listing"选项卡里勾上生成 map）：

```
Image component sizes
  Code (inc. data)   RO Data    RW Data    ZI Data      Total
  当前工程：xxx        xxx        xxx        xxx
```

记两个数：**RW Data + ZI Data**（运行时内存占用）。这就是你的"存款余额"。

### 第二步：裁剪决策表

SDK 的功能由配置文件里的宏决定开关。每一个宏打开，都意味着 RAM 或 Flash 的支出。以产品的真实处境（SRAM 3 KB，栈已占 1 KB）做决策：

| 宏 | 功能 | 去留 | 理由 |
|---|------|------|------|
| `WIFI_CONTROL_SELF_MODE` | MCU 自主控制 Wi-Fi 电源 | **必留** | 低功耗产品的命门——事件驱动架构（第 7 篇）的前提 |
| `DO_CACHE_SUPPORT` | DP 离线缓存 | **必留** | 面板下发的设置在云端，设备醒来要拉缓存同步（第 11 篇） |
| `SUPPORT_MCU_FIRM_UPDATE` | MCU OTA 升级 | **留** | 固件要可持续维护（第 16 篇） |
| `WIFI_MODULE_UPDATE` | Wi-Fi 模组自升级 | 砍 | 与本产品无关，模组升级不由 MCU 管 |
| `SUPPORT_MCU_RTC_CHECK` | RTC 时钟校验 | 砍 | 产品没有时间显示需求，省 RAM |
| `WIFI_TEST_ENABLE` | SDK 自带产测 | 砍 | 它的命令字和别的东西撞车，产品后来自己重做了产测（第 17 篇细说） |
| `WIFI_QUERY_ROUTE_RSSI` | 查询路由信号强度 | 砍 | 产测需求，按需再说 |

**决策原则就一条：每个功能都要能回答"砍掉会失去什么、留下能换来什么"。** 答不上来的，砍。

### 第三步：编译，看账

裁剪完编译，再打开 .map 对比：**RW+ZI 涨了多少？缓冲区大头是哪些？** SDK 的串口收发缓冲、DP 缓存、协议解析缓冲会明晃晃地列在那里。

产品的真实账：裁剪完成后，SDK 相关缓冲区约 300+ 字节，整机 RW+ZI 约 1.9 KB——在 3 KB 限额内，但余量已经以"百字节"计。**从这里开始，每加一个功能都要先问一遍预算**，这个习惯会贯穿整个系列。

## 四、烧录与验收：对手戏第二季

- [ ] 移植完成编译零报错后，串口助手扮演模组发心跳 `55 AA 00 00 00 00 00`——**这次你没有写任何回复代码**，但助手收到了 SDK 自动回复的 `55 AA 03 00 00 00 03`；
- [ ] 助手发工作模式查询 `55 AA 00 02 00 00 01`，SDK 自动回复（含配置好的工作模式）；
- [ ] 应用层调用 `mcu_dp_value_update(1, 250);`（上报温度 25.0℃），逻辑分析仪或助手抓到一帧 `55 AA 03 07 ...`（0x07 = DP 上报命令字）——**你调了一行 API，SDK 替你完成了第 8 篇里 tuya_send_frame 的全套工作**；
- [ ] 助手伪造一条 DP 下发帧（改 App 温度上限），断点停在 `dp_download_handle()`，确认能收到且 dpid 正确；
- [ ] 更新后的 .map 里，能指着缓冲区条目说出每个大概是谁、为什么这么大。

## 五、原版对照（CIU32F003）

产品 SDK 集成的完整形态，在四个对接点之外还有两个产品化细节：

1. **对接点②接得更深**。产品的串口 RX 中断就是直接把字节喂 `uart_receive_input()`，但喂之前工程里加了一道长度防线——超长的畸形帧直接拒收，不打扰 SDK。SDK 默认信任输入，真实总线上的输入不值得信任；
2. **全量上报走单帧**。SDK 的逐 DP 上报接口 `mcu_dp_*_update()` 会一 DP 一帧地发，产品在大批量上报时没用它，而是自己组了一帧包含全部 14 个 DP 的 0x07 大帧——为什么这么做、怎么做，第 11 篇专讲（它背后是"连续多帧会丢"的真实教训）；
3. **版本号纪律**。`MCU_VER` 与 Bootloader 里的版本宏必须保持一致（第 16 篇发版时会强调，这里先记账）。

## 六、彩蛋：三个字母的宏，藏着一个静默杀手

产品 SDK 移植完成后，功能一切正常：单 DP 下发、上报、心跳、握手……直到测试同学做了一项测试：**App 上同时改两个设置**（比如温度上限和湿度上限一起下发）。结果——设置没生效。没有报错、没有异常帧、串口上干干净净，就是"没反应"。单改一个，好使；两个一起改，静默失败。

抓帧发现：两个 DP 合并成一帧下发，长度超过了某个阈值，帧被 SDK **无声无息地拒收**了。追进 SDK 源码，找到拒收的长度守卫，再往上追缓冲区的定义，真凶现形——SDK 移植配置里一个宏的**定义位置**写错了：

```c
#if   (SUPPORT_MCU_FIRM_UPDATE == 1)
  #define 各种缓冲区 大
#elif (SUPPORT_MCU_FIRM_UPDATE == 2)
  #define 各种缓冲区 中
#else
  #define 各种缓冲区 小        ← 实际走了这里！
#endif

/* ……几十行之后…… */

#ifndef SUPPORT_MCU_FIRM_UPDATE
#define SUPPORT_MCU_FIRM_UPDATE    1
#endif
```

看出来了吗？**判断在前，定义在后**。C 预处理器从上往下扫，走到 `#if` 时宏还不存在，条件全不成立，缓冲区全部按"小"分配——实际生效的接收缓冲只有二十几个字节，比一帧双 DP 下发还小。长度守卫尽职尽责地拒收了超长的帧，而守卫背后的真相是缓冲区被人偷偷缩了水。

修复只需要把宏定义挪到判断**之前**——但查清"为什么多 DP 下发会静默失败"花了整整一条排查链：抓帧 → 发现无回复 → 读 SDK 源码 → 长度守卫 → 缓冲区定义 → 宏顺序。链条上任何一环松手，这个 bug 就会流进量产固件，变成客服热线里的"有时设置不管用"。

两条教训请刻下来：

1. **宏的依赖顺序是真实存在的坑**，`#if` 依赖的宏必须在前面定义——编译器不会替你检查"这个宏是不是后定义的"；
2. **"静默失败"是嵌入式最贵的 bug 类型**。报错、异常、复位，都好查；悄无声息地不工作，排查成本十倍起。写代码时主动问自己一句："这条路失败了，谁看得见？"

## 七、下篇预告

SDK 转起来了，功能也裁剪明白了。但移植完成不等于太平——第 10 篇是全系列的"名篇"：《破案：7 个字节引发的"恢复出厂"》。回到第 8 篇埋下的那条校验和对不上的空帧，我们完整复盘一场真实"大案"：用户在 App 上设好的阈值总是神秘复原，团队查了存储、查了云端、差点怀疑人生，最后凶手就藏在 SDK 解析空数据帧的一行代码里。下一篇，当一回嵌入式侦探。
