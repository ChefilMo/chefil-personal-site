## 一、整机联调：当所有模块一起说话

前 12 篇是"分而治之"——每个模块单独讲透。但真实的困难在联调：**模块各自正确 ≠ 整机正确**。模块间的共享资源、时序耦合、状态依赖，只有全速跑起来才会暴露。

本项目的整机联调检查表（按依赖顺序）：

### 1.1 启动序列（上电 3 秒内）

调试串口应有的完整时序，精简成文字时间线：

1. `first init` —— UART 初始化、log 系统就绪，打印应用版本号；
2. `second init` —— Zigbee 端点/簇注册、三连上电配网检测；
3. `third init` —— LED/按键 GPIO 初始化；
4. `last init` —— 数据模型、发送队列、两颗计量芯片、LCD 依次初始化；
5. 初始化段的前后时间戳差值应 **< 100ms**——这是第 02 篇"init 不做耗时操作"纪律的验证手段：同步初始化（SPI 计量芯片 + UART 计量芯片 + LCD）必须在百毫秒内完成，剩下的异步任务（计量芯片校验、首次采集）交给定时器；
6. 上电约 200ms 后，异步启动计量芯片的校验流程。

### 1.2 稳态运行（入网后）

每 10 秒一个采集周期，log 节奏应该是：先打印聚合后的三相电压/电流/总功率与温度（`all_ok` 标志位必须盯——它是"本周期所有相都读成功"的总闸），随后是死区过滤后实际发出的 DP 上报帧，最后是逐帧的发送队列确认。三行 log 一一对应：**采集 → 过滤 → 送达**，任何一环静默都是故障信号。

### 1.3 资源冲突矩阵

联调时最要盯的是**共享资源**，一张表自检：

| 资源 | 使用者 | 冲突场景 | 解决方案 |
|------|--------|---------|---------|
| UART0 | 计量芯片（UART 款） | 早期 log 与其抢 | log 移到模拟串口引脚 |
| 软件定时器池 | 全部模块 | 定时器泄漏/重复使用 | 每个模块自己 create，stop 后再 start |
| Flash | OTA / KV 存档 | OTA 期间写 KV 变砖 | OTA 回调里停所有定时器 |
| 计量芯片状态机 | verify / calc / re-init | 重入卡死 | busy 标志 + 统一入口检查 |
| Zigbee 发送队列 | DP 队列 / 应答 | zcl_id 互相清除 | 队列与应答各用独立 zcl_id |
| 全局数据模型 | 采集写 / 上报读 / LCD 读 | 数据撕裂 | 单线程事件驱动，天然无竞态（ISR 只写自己的缓冲） |

最后一行值得展开：本项目没有加任何互斥锁，因为**整个架构是单线程事件驱动的**——所有对共享数据模型的访问都发生在主事件循环（定时器回调、消息回调）里，ISR（UART RX、按键 IRQ）不碰共享数据，只往自己的私有缓冲写。**"用架构消灭锁"比"到处加锁"高明得多。**

## 二、量产之路：从开发板到产品

### 2.1 授权烧录（绕不开的 7 天限制）

第 01 篇提过：BDT 直接烧录的固件最多运行 7 天。这是涂鸦的授权机制——正式产品必须把授权信息（与 PID 绑定的密钥）写入 Flash 指定区域，固件启动时校验。

量产流程：

1. 涂鸦 IoT 平台提交产品认证，获取授权烧录工具（云端生成授权码）；
2. 产线 PC 装授权烧录工具，烧录 QIO bin + 写入授权；
3. 每台设备首次联网时向涂鸦云注册激活。

开发调试阶段不用管授权（7 天够调了），但送样/量产前必须完成认证——**把这个排进项目计划，认证周期往往比想象中长**。

### 2.2 产线测试流程

结合第 10/11 篇的自检功能，一条最小产测工位：

```
1. 烧录授权固件，上电
2. 检查 LCD 显示全零（不是黑屏/乱码）
3. 三击按键 → 全笔画 → 肉眼检段
4. 接标准负载（220V/89W），双击 ×3 依次测 A/B/C 相
   → 每相 LED 闪 5 次 = 合格
5. 夹具触发三连上电 → 进入配网 → 测试网关确认设备上线、38 个 DP 上报正确
6. 拆夹具，贴标
```

全流程不到 2 分钟，覆盖显示、计量、通信三大功能。

### 2.3 出厂默认配置

数据模型的初始化默认值就是出厂语义：功率阈值 500W、开关 OFF、全部校准 0。恢复出厂（第 04/08 篇的三重清零）把设备拉回这个状态。**默认值表要在产品文档里显式维护**——"恢复出厂后设备是什么状态"是客服电话的高频问题。

## 三、项目进化史：整个开发过程里的工程课

回看整个开发过程，这个项目的演进本身就是一部微缩的嵌入式开发史。按主题归类三个阶段：

### 3.1 "能跑"到"跑得稳"

这一阶段的修复记录：DP 发送队列（从"错峰玄学"到"有背压的队列"）、队列死锁修复（应答与队列 zcl_id 隔离 + 看门狗）、上报死区与报警单位修正（从"全量狂发"到"变化才报"）、首次上报全量快照机制。

主题词是**可靠性**：发送要有队列、失败要有重试、回调要有看门狗、上报要有死区、首次要有全量。每一课都是" naive 实现 → 线上故障 → 机制修复"的完整闭环。

### 3.2 "单点"到"系统"

这一阶段的修复记录：配网期间停止采集（网络状态机开始调度业务）、计量芯片故障自愈（从"死了等人工"到"三级自动恢复"）、断网保持采集（离线 ≠ 停工）、LED 反馈 + NTC 检测（每个状态都有视觉语言）。

主题词是**系统思维**：模块不再各自为政，网络状态决定业务启停，故障有分级恢复策略，用户能从 LED 读懂设备在想什么。

### 3.3 "功能"到"产品"

这一阶段的修复记录：电表自检（产线可测）、校准立即可见（UX 闭环）、LCD 离线修复（双份状态同步）、首次配网上报加固（延迟 6s + 备份上报）、OTA 三连修（心跳/定时器/设备类型）、三击全笔画（产线检验工具）。

主题词是**产品化**：可生产、可校准、可升级、可检验。

### 3.4 方法论沉淀

整个开发过程里反复出现的几条原则，值得任何嵌入式项目借鉴：

1. **一切异步回调都有超时兜底**（看门狗思想）——计量状态机、DP 队列、OTA 皆是；
2. **校验和防损坏、防不了错位**——协议层要靠清场（ring clear）和全成功才提交（all_ok）防御时序问题；
3. **数值进系统前过"物理合理性"检查**——死区、钳位、NTC 开路哨兵值；
4. **软件镜像与硬件状态必须同步**——LCD 双份状态之坑；
5. **事件不能丢、高优先级要抢占**——LED 的 target/current 双模式；
6. **影响安全的输入变化立即重判**——阈值修改不等周期；
7. **用架构消灭锁**——单线程事件驱动 + ISR 私有缓冲。

## 四、如果重来一次：改进清单

诚实的复盘——这些是当前代码的已知边界，也是读者可以自己动手的方向：

### 4.1 架构层

- **计量芯片的同步读取代码已成死路**。同步读寄存器系列原语还在，但业务全走异步状态机。按"修复后移除旧实现"的原则，应该删掉同步路径（约 400 行）——留着它们只会让后来人误用；
- **两颗计量芯片的驱动文件已超可维护阈值**（一个 2500+ 行、一个 1700+ 行）。两颗芯片的寄存器表、换算公式大量重复，可以抽一个公共层——不过要警惕"抽象层只服务两个实例"的过度设计，当前拆不拆是个见仁见智的问题；
- **报警滞回**（第 11 篇提过未实现）：阈值 ±5% 双阈值可消除边界抖动。

### 4.2 功能层

- **芯片系数层校准**（写系数寄存器）：当前加性校准不覆盖比例误差，量产高精度场景需要；
- **差分 OTA**：TLSR8258 平台当前不支持，大固件全量升级在弱信号网络里耗时长；
- **电量变化上报实时化**：当前电量只在 10s 周期上报，改成"电量每变 0.01kWh 立即报"可让 App 电量曲线更平滑——代价是帧率上升，需配合死区策略。

### 4.3 工程层

- **单元测试缺失**。所有验证靠整机 log——单线程事件驱动代码其实很适合做"事件回放"测试（把定时器回调序列化录下来回放），但本项目没做；
- **调试日志级别未分级**。调试打印一把梭，量产固件应该能把调试日志编译出去（总开关宏已有，但模块级开关没有）。

## 五、给想动手的朋友：复现路线图

如果你想复现或改造这个项目，按这个顺序投入时间最省：

```
第 1-2 周：环境 + 生命周期 + 配网（第 01-04 篇）
          → 目标：App 上看到设备在线
第 3-4 周：DP 协议 + 数据模型（第 05、08 篇）
          → 目标：App 能控制一个虚拟 DP（比如先用随机数代替真实计量）
第 5-6 周：SPI 计量芯片一路通道（第 06 篇）
          → 目标：单相真实数据上云
第 7-8 周：UART 计量芯片 + LCD（第 07、10 篇）
          → 目标：三相数据 + 本地显示
第 9-10 周：报警/校准/OTA（第 11、12 篇）
          → 目标：功能完整
持续：第 09 篇的队列和第 13 篇的联调清单贯穿始终
```

**关键建议：先用随机数/固定值打通全链路，再接入真实硬件。** 第 05 篇提到的测试值强制全量上报工具（填 222.2V/1111mA 等可识别测试值）就是为这个目的保留的调试手段——数据链路有问题时，它能把"通信故障"和"计量故障"干净地分开。

## 六、尾声

这个项目从灯光 demo 的三行修改开始，到一台能自检、能校准、能跳闸、能 OTA 的三相电表结束。回头看你也许会同意：**嵌入式开发的难度不在任何单个知识点，而在于让所有约束同时成立**——Flash 寿命要和电量精度平衡，异步回调要和状态一致性平衡，15 个槽位要和 38 个 DP 平衡，成本要和可靠性平衡。

每一篇里的"踩坑实录"，本质上都是一次约束冲突的解决记录。希望这个系列能让你少踩几个我们踩过的坑，多踩几个属于你的新坑——那才是这个行当真正的乐趣。

系列完。固件不息，折腾不止。
