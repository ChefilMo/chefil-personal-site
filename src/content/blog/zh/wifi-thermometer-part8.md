## 一、本篇目标与效果

**目标**：手写一个涂鸦协议帧解析器 + 组帧器，实现：

1. 串口助手发一条"工作模式查询"（`55 AA 00 02 00 00 01`），单片机正确解析并回复约定帧；
2. 串口助手发心跳，单片机回心跳；心跳中断 3 秒，单片机告警"和模组失联了"；
3. 故意发一个校验和错误的帧，单片机拒收并打印原因。

**做完你会懂**：帧格式每个字节的分工、校验和怎么算、接收状态机怎么写、以及"握手"这个词在协议里的具体含义。

## 二、原理 10 分钟

### 2.1 为什么要"帧"：从字节流到消息

第 2 篇的串口是字节流：你不知道哪几个字节算一条完整消息。通信协议的第一件事就是**给字节流画边界**——把字节打包成"帧"。涂鸦协议的帧结构：

```
┌────────┬────┬──────┬───────┬──────────┬───────┐
│ 帧头    │ 版本│ 命令字│ 数据长度│  数据区   │ 校验和 │
│ 55 AA  │ 1B │ 1B   │ 2B    │ 0~N 字节 │ 1B    │
└────────┴────┴──────┴───────┴──────────┴───────┘

校验和 = (版本 + 命令字 + 长度高 + 长度低 + 所有数据字节) & 0xFF
```

逐字节拆解一条真实帧（模组上电会问 MCU 的第一句话——**工作模式查询**）：

```
55 AA 00 02 00 00 01
│  │  │  │  │  │  └─ 校验和：00+02+00+00 = 02？ 注意！
│  │  │  │  │  └──── 数据长度低字节 = 0
│  │  │  │  └─────── 数据长度高字节 = 0
│  │  │  └────────── 命令字 = 0x02（工作模式查询）
│  │  └───────────── 版本 = 0x00（模组发起的帧用 0x00）
│  └──────────────── 帧头第二字节（固定 AA）
└─────────────────── 帧头第一字节（固定 55）
```

校验和是从**版本字节开始**累加：这里 `0x00 + 0x02 + 0x00 + 0x00 = 0x02`——咦，帧里最后是 `0x01`？

……别急，先记住这个矛盾。本篇第 2.3 节会给你答案，它是第 10 篇一场大案的第一条线索。

三条规则先立住：

1. **帧头两个固定字节** `55 AA`——找帧的起点；
2. **长度字段说了算**——数据区多长由它声明，解析器按它收数据；
3. **校验和是底线**——任何一位在传输中受了干扰，校验和都对不上，帧必须丢弃。

### 2.2 接收状态机：按字段顺序"吃"字节

字节是一个一个来的，解析器用一个小状态机逐字节推进：

```
WAIT_55 ──55──▶ WAIT_AA ──AA──▶ VER ──▶ CMD ──▶ LEN_H ──▶ LEN_L
   ▲                                  │
   │                                  └── 按 len 收 DATA ──▶ CHKSUM
   └────────── 任何一步不符合预期，回到 WAIT_55 ─────────┘
```

"任何一步不符合预期就回到找帧头"——这一条让解析器天然具备了**抗干扰自愈能力**：总线上有噪音字节、有残帧，都会被逐字节抛弃，等待下一个干净的 `55 AA`。

### 2.3 心跳与工作模式查询：模组的两个开场问题

涂鸦低功耗协议的握手由模组主导，开场白两连问：

**① 工作模式查询（0x02）**：模组上电就问："咱俩谁说了算？"MCU 必须在约定时间内回复自己的工作模式，否则模组认为对面没人，反复重问（甚至卡死在初始化）。

**② 心跳（0x00）**：握手之后，模组周期性发心跳帧，MCU 必须原样回复。心跳的意义两个字：**活着**。哪一方连续几次收不到心跳，就可以判定对方掉线——对低功耗产品，MCU 用心跳监测"模组是不是还在认真干活"，模组用心跳决定"能不能放心睡"。

MCU 回复帧的版本字节是 **0x03**（与模组发起帧的 0x00 不同，这是协议的角色约定）。以心跳回复为例，亲手算一遍校验和：

```
版本  命令  长度H 长度L      累加
 03 + 00 +  00  +  00   =  03   → 帧：55 AA 03 00 00 00 03
```

## 三、动手写代码

### 第一步：组帧器（发送用）

```c
static void tuya_send_frame(uint8_t ver, uint8_t cmd,
                            const uint8_t *data, uint16_t len)
{
    uint8_t sum = 0;
    uart_putc(0x55); uart_putc(0xAA);
    uart_putc(ver);  sum += ver;
    uart_putc(cmd);  sum += cmd;
    uart_putc((uint8_t)(len >> 8)); sum += (uint8_t)(len >> 8);
    uart_putc((uint8_t)(len & 0xFF)); sum += (uint8_t)(len & 0xFF);
    for (uint16_t i = 0; i < len; i++) {
        uart_putc(data[i]); sum += data[i];
    }
    uart_putc(sum);
}
```

### 第二步：接收状态机（在 10ms tick 里驱动）

```c
typedef enum {
    RX_55 = 0, RX_AA, RX_VER, RX_CMD, RX_LENH, RX_LENL, RX_DATA, RX_SUM
} rx_state_t;

typedef struct {
    rx_state_t state;
    uint8_t  ver, cmd, lenh, lenl, sum;
    uint8_t  data[32];
    uint16_t idx;
} rx_t;

static rx_t s_rx;

static void rx_reset(void) { s_rx.state = RX_55; s_rx.sum = 0; s_rx.idx = 0; }

/* 每收到一个字节喂进来 */
static void rx_feed(uint8_t b)
{
    switch (s_rx.state) {
    case RX_55:  if (b == 0x55) s_rx.state = RX_AA; break;
    case RX_AA:  if (b == 0xAA) { s_rx.state = RX_VER; s_rx.sum = 0; }
                 else rx_reset(); break;
    case RX_VER: s_rx.ver = b; s_rx.sum += b; s_rx.state = RX_CMD; break;
    case RX_CMD: s_rx.cmd = b; s_rx.sum += b; s_rx.state = RX_LENH; break;
    case RX_LENH:s_rx.lenh = b; s_rx.sum += b; s_rx.state = RX_LENL; break;
    case RX_LENL:{
        s_rx.lenl = b; s_rx.sum += b;
        uint16_t len = ((uint16_t)s_rx.lenh << 8) | s_rx.lenl;
        if (len == 0)      s_rx.state = RX_SUM;
        else if (len > 32) rx_reset();              // 超长帧：不可能，丢弃
        else               { s_rx.idx = 0; s_rx.state = RX_DATA; }
        break;
    }
    case RX_DATA:
        s_rx.data[s_rx.idx++] = b; s_rx.sum += b;
        if (s_rx.idx >= (((uint16_t)s_rx.lenh << 8) | s_rx.lenl))
            s_rx.state = RX_SUM;
        break;
    case RX_SUM: {
        uint8_t frame_sum = s_rx.sum;               // 本地累加值
        if (frame_sum == b) on_frame_ready(&s_rx);  // 校验通过，交业务层
        else uart_puts("[rx] checksum error, dropped\r\n");
        rx_reset();
        break;
    }
    }
}
```

### 第三步：业务分发 + 心跳监测

```c
static uint32_t s_last_heartbeat_ms = 0;

static void reply_work_mode(void)
{
    uint8_t mode = 0x00;                 // 0x00 = MCU 配合处理模式（语义见原版对照）
    tuya_send_frame(0x03, 0x02, &mode, 1);
    uart_puts("[tx] work mode reply\r\n");
}

static void on_frame_ready(rx_t *f)
{
    switch (f->cmd) {
    case 0x00:                                  // 心跳
        tuya_send_frame(0x03, 0x00, NULL, 0);
        s_last_heartbeat_ms = s_now_ms;
        uart_puts("[rx] heartbeat\r\n");
        break;
    case 0x02:                                  // 工作模式查询
        reply_work_mode();
        break;
    default:
        uart_puts("[rx] unknown cmd\r\n");
        break;
    }
}
```

主循环里（第 7 篇的窗口 tick 里）加失联监测：

```c
if (s_now_ms - s_last_heartbeat_ms > 3000) {
    uart_puts("!! heartbeat lost\r\n");
    /* 产品里这里会触发 Wi-Fi 状态置为未知（第 11 篇展开） */
}
```

## 四、烧录与验收：人机对手戏开场

接线：CH340 模块 TX/RX 交叉接 PA10/PA9（和第 2 篇相同），串口助手设 **9600-8-N-1、十六进制显示和发送**。

- [ ] **开场白**：助手发送 `55 AA 00 02 00 00 01`（注意勾选"十六进制发送"），单片机串口打印 `[tx] work mode reply`，且助手收到回复帧 `55 AA 03 02 00 01 00 06`——**亲手用计算器验算一下回复帧的校验和**（03+02+00+01+00 = 06）；
- [ ] **心跳**：助手发 `55 AA 00 00 00 00 00`，单片机回 `55 AA 03 00 00 00 03`；
- [ ] **失联告警**：停止发心跳，3 秒后单片机打印 `!! heartbeat lost`；
- [ ] **校验防线**：把第一条查询帧的最后一个字节改成 `02` 再发，单片机打印 `checksum error, dropped`，不做任何回复；
- [ ] **逻辑分析仪彩蛋**：抓下这组对话的波形，你能亲眼看到 `55 AA` 起始、9600 波特率下一个 bit 约 104µs——协议文档上的每个数字第一次变得立体。

**排障提示**：单片机回复了但助手显示乱码 → 检查助手是不是设成了 9600（第 2 篇的肌肉记忆）。助手发了没反应 → 九成是忘了勾"十六进制发送"，助手把字符串"55 AA..."的 ASCII 码发出去了。

## 五、原版对照（CIU32F003）

产品对接真实涂鸦模组，本篇的每个元素都有对应，差异在深度：

1. **版本号 0x03 是硬性要求**。产品调试时真踩过：MCU 回复帧版本字节写错过，模组对不上"口音"，握手永远失败，模组疯狂重发 0x02——现象就是"串口上全是查询帧，MCU 也在回，但没完没了"。协议里的每个固定字段都是暗号，错一个就是两个世界；
2. **0x02 回复的内容不是随便填的**。产品选择的是"MCU 配合处理模式"——Wi-Fi 的状态灯、复位等行为由 MCU 配合控制，这是低功耗产品的标准姿势（配网时保持唤醒那套逻辑就靠它）；
3. **产品多了个"握手完成标志"**。解析层收到 0x02 回复成功的确认后，才置位这个标志；**标志置位前，禁止上报任何 DP 数据**——否则模组还没进入工作状态，帧发了也白发，还互相干扰。一条"标志位+检查点"的纪律，解决了一大类时序 bug；
4. **心跳监测的用途更深**。产品用心跳判断模组是否健在，一旦失联，联网状态图标按"未知"处理（Wi-Fi 图标不瞎显示旧状态）——这个细节第 11 篇还会展开。

## 六、彩蛋：那个算不对的校验和，是个伏笔

回到 2.1 节埋下的矛盾：`55 AA 00 02 00 00 01`，按规则算校验和应该是 `0x00+0x02+0x00+0x00=0x02`，帧里却写着 `0x01`。

这条帧不是我编错了——**它是真实产品日志里抓出来的、模组上电后实实在在会发的帧**，而且 `01` 这个值有讲究：它恰好是涂鸦协议里"AP 配网状态"的编号。

一个校验和对不上的帧，内容里藏着一个有语义的状态值……如果你在产品的代码里直接把"校验和位置的字节"读出来当数据用，会发生什么？

我先卖个关子。第 10 篇《破案：7 个字节引发的"恢复出厂"》，我们会完整复盘这场真实发生过的"大案"：用户 App 上改的设置一次次变回默认值，团队怀疑过存储、怀疑过云端，最后凶手竟然是这条不起眼的空帧。到时候你会明白，为什么本篇反复强调"校验和是底线"——**协议里的每条纪律，都是某次事故的纪念碑**。
