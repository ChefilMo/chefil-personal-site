> 代码能跑、能睡、能升级，但"能跑"和"敢发货"之间隔着一条产线。工厂里的场景完全不同于开发台：操作员不是工程师，节拍以秒计，判断要声光明确，坏机必须当场拦下。
> 本篇是产品思维浓度最高的一篇：**怎么设计一套产测，让流水线上的普通人在几秒内判断一台设备是良是劣**。

---

## 一、本篇目标与效果

**目标**：学习版实现一个简化"产测模式"——上电自动跑自检序列：LCD 全显 → 蜂鸣短响 → 串口输出自检报告（传感器在线、按键通断、ADC 读数），人为拔掉传感器能看到报告从 PASS 变 FAIL。

**做完你会懂**：产测设计的四条原则（快、明确、一次一判、不依赖公网）、0x0e 路由扫描的原理、以及发版流程的纪律。

## 二、原理 10 分钟

### 2.1 产测在回答什么问题

产测不回答"这台设备完不完美"，只回答一个二元问题：**这台能不能发货**。一切设计围绕这个目标的四个约束：

1. **快**：流水线节拍可能只有 10~30 秒/台，测试项必须按秒设计，能合并的合并（一次上电查全部）；
2. **明确**：结果必须是声光级的——响一声是过，滴滴滴是不过，操作员不需要看串口。第 15 篇"产线噪音"彩蛋的正面版：产测的提示音要**足够响、足够不同**；
3. **一次一判**：每台设备每次上电只做一次判定，不做第二次（防误判、防节拍失控），判定结果保持到断电——产测模式"进入即保持，退出靠复位"；
4. **不依赖公网**：真实产线可能没有外网。产品的核心测试项（Wi-Fi 射频好坏）用一个**指定产测路由**（SSID 固定为 `tuya_mdev_test`）在局域网内完成，云端不参与。

### 2.2 Wi-Fi 产测：0x0e 扫描的原理

怎么在产线验证"这台设备的 Wi-Fi 模组和天线是好的"？产品的方案是涂鸦协议的 **0x0e 产测扫描**命令：

```
MCU → 模组：55 AA 03 0E 00 00 10
                    ↑命令字0x0E，无数据区
模组 → MCU：扫描环境中是否存在 SSID "tuya_mdev_test"
            回复：result(找到与否) + rssi(信号强度)
判定：result==1 且 rssi ≥ 80 → Wi-Fi 链路合格
```

rssi 门槛为什么要 80 而不是"能连上就行"？因为产线上模组和路由的距离是**固定已知的**——这个距离下的信号强度有一个预期区间。信号弱于预期，说明这台的天线焊虚了、模组是次品、或者外壳装配出了问题。**产测的本质是和"已知良好的基准"做对比**，rssi 门槛就是这个基准的量化。

时序上有个讲究：0x0e 不能上电即发。Wi-Fi 模组启动、握手、稳定需要几秒，所以产品规定：**Wi-Fi 上电累计满 5 秒、且收到过模组的联网状态上报之后**，才发 0x0e——发早了模组不理你，会误判成 Wi-Fi 不良。

### 2.3 产测模式的行为清单

判定合格后，设备进入产测模式，这个模式本身就是一套"可操作的测试台"：

- **每秒滴一声**：状态指示——产线上几十台设备在一起，操作员循声就知道哪些在产测态（听觉是最不占手不占眼的通道）；
- **不进 Deepstop**：保持醒着，随时可操作，整机电流处于唤醒态（这也是"Wi-Fi 已关闭"的旁证——电流明显低于联网态）；
- **Wi-Fi 关闭**：扫描已完成，模组断电省电；
- **短按按键 → LCD 全显 5 秒**：目检所有笔画段，缺段（虚焊/屏裂/驱动问题）当场可见——第 13 篇"全显测试"从开发期延伸到了产线；
- **低电图标实时刷新**：可调电源降压到阈值以下，图标约 1 秒内点亮/熄灭，验证电量检测链路；
- **告警不叫**：产测环境下故意不触发告警蜂鸣，免得产线此起彼伏；
- **退出 = 复位**：没有"退出产测"的复杂操作，断电重上电就回到正常产品。

注意这套清单的设计美学：**每一项产测动作同时也是一个测试项**。滴一声（蜂鸣器好）、全显（LCD 好）、图标随电压变（ADC 好）、不进 Deepstop（低功耗链路好）……产测不是额外加的测试代码，而是把已有功能按产线场景重新编排。

## 三、动手写代码（学习版简化产测）

学习版没有 Wi-Fi 模组，产测聚焦"上电自检序列"——三幕，一气呵成：

```c
void factory_self_test(void)
{
    /* 第一幕：全显（LCD 自检） */
    lcd_all_segments_on();               // 1602 就逐格写满 '8' 字符
    beep_start(200, 200, 0);             // 一声短响（蜂鸣器自检）

    /* 第二幕：逐项自检，攒报告 */
    bool sensor_ok = (gxht40_read(&t, &h) == 0);     // I2C 链路 + 传感器
    bool key_ok    = wait_key_with_timeout(3000);    // 等操作员按键 3s
    uint16_t raw   = adc_read(1);                    // NTC 分压链路
    bool ntc_ok    = (raw > 100 && raw < 4000);      // 不在开短路区

    delay_ms(2000);                      // 全显保持 2 秒给目检留时间
    lcd_all_segments_off();

    /* 第三幕：串口输出报告（PASS/FAIL 一目了然） */
    uart_puts("=== FACTORY TEST ===\r\n");
    uart_puts(sensor_ok ? "SENSOR: PASS\r\n" : "SENSOR: FAIL\r\n");
    uart_puts(key_ok    ? "KEY   : PASS\r\n" : "KEY   : FAIL(timeout)\r\n");
    uart_puts(ntc_ok    ? "NTC   : PASS\r\n" : "NTC   : FAIL\r\n");

    /* 学习版没有真正的产测态，报告完继续正常流程；
       产品的产测态见原版对照 */
}
```

验收剧本：

- [ ] 完整组装：三幕按序执行，串口报告全 PASS；
- [ ] 拔掉 GXHT40 重启：报告 SENSOR: FAIL——**故障注入下产测的分辨力**；
- [ ] 上电后不按键：3 秒后 KEY: FAIL(timeout)——超时即判，不无限等（第 6 篇"一切等待必须可超时"的产测版）；
- [ ] 短接 NTC 两端（模拟探头短路）：NTC: FAIL——第 4 章的开短路保护在产测里直接复用。

## 四、原版对照（CIU32F003）

把学习版的思维放大到产品全貌，产测是三个层次：

**层次一：0x0e 射频测试**（上文详述）。补两个产品细节：扫描等待期间**UART 窗口顺延**——0x0e 回复没到时不许进 Deepstop，回复会被截断（又是截断，第 2/5/15 篇的老朋友）；rssi 门槛在试产中从 60 提到 80——低门槛放过了一批"天线偏弱但能连"的边缘机，用户家里路由远一点就掉线，投诉教做人。

**层次二：产测模式**（上文 2.3 的完整清单）。产品还加了一条：产测期间**每约 1 秒执行一次完整测量**（温湿度、电池全采一遍），LCD 持续刷新——操作员把设备放进温箱/对着空调口，能直观看到读数在变，传感器链路的好坏一目了然。

**层次三：全量冒烟清单**。开发侧的验证是 14 项清单（Wi-Fi 电源通断、串口波形、I2C ACK、NTC、电池电压、LPTIM 周期、Deepstop 电流、面板 DP、长按配网、五连击 OTA、OTA 升级全流程、蜂鸣器、产测、无路由不进入产测）——每项一个可勾选的验收语句。**清单的价值不在"跑一次"，在"每次发版后重跑一次"**：它是产品的回归测试底座。

**发版流程**（收束第 9、16 篇伏笔）：版本号两处（App `MCU_VER`、Bootloader 版本宏）同步递增 → 先后构建两个工程 → 烧录两份 hex（Bootloader + App）→ 追加版本记录 → 14 项清单全过 → 封样。任何一步偷懒（常见的是忘了同步版本号），后续 OTA 链路必然出灵异问题。

## 五、彩蛋：0x0e 的"出身"——一个被放弃的 SDK 功能

第 9 篇裁剪表里埋过一行的 `WIFI_TEST_ENABLE`：SDK 自带 Wi-Fi 产测功能，产品把它砍了。原因本篇可以讲透了：**SDK 产测用的命令字和 DP 上报冲突**——低功耗协议的命令字空间里，SDK 自带的产测命令和正常业务帧撞车，开启它意味着某些正常帧会被误解析成产测帧。在"协议正确性"和"用现成功能"之间，产品选择了前者：关掉 SDK 的产测，用协议里的正式产测命令字 **0x0e** 自己实现了一遍。

这个取舍的普适教训：**SDK 给的功能是"平均场景的正确解"，不是"你场景的正确解"**。当 SDK 功能与你的产品约束冲突时，自己实现一条路并不丢人——丢人的是明知冲突还硬用，把灵异问题留给量产后的客服。

第二个小彩蛋关于"每秒滴一声"：最初版本没有它，产测静默进行，结果产线上出过"操作员以为设备死机、重复上电"的误会。加上周期性提示音后误会消失——**状态可见性（哪怕是听觉通道）是交互设计的元规则**，对操作员和对用户一样成立。
