> 目标：让数据可信（校准）、让超限可断（报警 + 继电器跳闸），以及“加性偏移”这种务实校准方案的来龙去脉

## 一、电表为什么必须能校准？

计量芯片出厂时自带校准系数（第 06 篇的 0x70-0x77 寄存器），但那是**芯片层面**的校准，只保证“ADC 计数 → 标准物理量”的换算准确。整机装出来之后，误差来自整个信号链：

```
电网电压 → 分压电阻(±1%) → 芯片 ADC → 换算值
负载电流 → 分流器/CT(±1%) → 芯片 ADC → 换算值
```

电阻的温漂、焊接阻抗、PCB 布局都会引入 1%~5% 的系统误差。芯片校准救不了这些——必须有一个**整机级**的校准机制：拿一个标准源（或标准表）做参考，量出偏差，存下来，运行时扣掉。

本项目支持 7 项整机校准：

| DP | 名称 | 范围 | 单位语义 |
|----|------|------|---------|
| 132 | 电压校准 | -50 ~ +50 | ±5V（scale=0，代码 ×0.1） |
| 133-135 | A/B/C 电流校准 | -200 ~ +200 | ±200mA |
| 136-138 | A/B/C 功率校准 | -50 ~ +50 | ±5W |

用户在 App 上填偏差值（比如标准表读 221.5V、设备读 220.8V，偏差 +0.7V → 填 7），网关下发 DP，设备持久化并在每次换算后叠加。

## 二、校准的实现：加性偏移的务实选择

### 2.1 为什么不用乘法校准？

教科书上的校准通常是乘性的（`实际值 = 读数 × 校准系数`），能修正比例误差。本项目选了**加性偏移**（`实际值 = 读数 + 偏移`），看 C 相的写入点：

```c
F_AC_V_8110  += meter->voltage_calibration * 0.1f;    /* DP 值 ±50 → ±5.0V */
F_AC_I_8110  += meter->current_calib_c  * 0.001f;     /* ±200 → ±0.2A */
F_AC_P_8110  += meter->power_calib_c    * 0.1f;       /* ±50 → ±5.0W */
```

加性方案的理由：

1. **误差来源以零点偏移为主**。分压电阻的比值误差（乘性）通常 <1%，而零点漂移、ADC 偏置、整流压降是固定的加减项——对民用表计，加性校准覆盖了主要误差；
2. **乘性校准在小信号时会放大噪声**。读数 0.3A 时 ×1.05 = 0.315，合理；但加性方案 0.3 + 0.05 = 0.35，对零漂的处理更直观可控；
3. **实现最简单，调试最安全**。加性偏移一眼能看懂，乘性系数填错（比如填 0 而不是 1）直接读数归零，加性填 0 就是“不校准”，天然安全。

代价是不能修正比例误差。如果实测发现“220V 时准、110V 时偏 5%”，那就是比例问题，得回芯片系数层去校（写 0x70-0x77——本项目代码保留了通用写原语但没实现该流程，属于量产化时的增强项）。

### 2.2 校准的持久化与即时生效

校准值是 RW 配置，走第 08 篇的标准流程：DP 下发 → `app_meter_data_set_dp` → 立即写 KV 0x10。重启后 `__meter_rw_load_from_kv` 恢复。

**“校准后立刻能看到效果”是个真实的 UX 需求**（项目实际的修复记录里就有这一笔）：用户在校准界面改完值，回头看实时数据面板——数据没变化！为什么？

第 08 篇讲过周期上报有**死区过滤**（电压变化 ≥10V 才报）。校准微调 1-2V，被死区吞了。修复：

```c
/* 校准类 DP 写入后，重置 first-report 标志 */
switch (dpid) {
case DP_ID_VOLTAGE_CALIBRATION:
case DP_ID_CURRENT_CALIBRATION_A: ... case DP_ID_POWER_CALIBRATION_C:
    sg_realtime_report_initialized = FALSE;    /* 下一次周期上报走全量分支 */
    break;
}
```

标志一清，下次 `app_meter_data_report_realtime` 进入“首次全量快照”分支，所有实时数据无条件上报——用户在 App 上 10 秒内就能看到校准效果。**机制复用是最优雅的修复**：没有新增任何上报路径，只是重置了一个标志位。

## 三、功率报警：阈值比较与继电器跳闸

### 3.1 报警判定

三相各自的功率超过各自阈值即报警（`app_meter_data_update_alarms`）：

```c
VOID_T app_meter_data_update_alarms(VOID_T)
{
    sg_meter_data.power_alarm_a = (abs(sg_meter_data.power_a) > sg_meter_data.power_setting_a * 10) ? TRUE : FALSE;
    /* B、C 同理 */
    ...
}
```

两个细节：

- **绝对值比较**：反向功率（发电）也算超限。用户侧光伏并网的时代，反向超限保护是刚需；
- **量纲换算**：`power_setting_a` 是整数 W（scale=0），`power_a` 是 W×10（scale=1），所以阈值 ×10 对齐。量纲不一致是本项目的隐藏复杂度——所有比较点都要先对齐 scale。

报警的派生位置值得说明：`update_alarms` 在**聚合层**被调用（`__aggregate_meter_data` 第 ④ 步），每次新数据进来就重算。为什么不放在 DP 下发处（阈值被修改时算一次）？因为功率是动态变化的，阈值不变功率也可能越线——必须每个采集周期重判。

### 3.2 跳闸：断路器语义的软件实现

超限后干什么？本项目的选择是**继电器强制断开 + 状态锁存**：

```c
BOOL_T any_alarm = power_alarm_a || power_alarm_b || power_alarm_c;

/* 断路器跳闸语义：任一相超限且继电器当前闭合 → 锁存断开 */
if (any_alarm && sg_meter_data.switch_state) {
    sg_meter_data.switch_state = FALSE;      /* 锁存：用户必须手动重新合闸 */
    __meter_rw_save_to_kv();                 /* 掉电也保持跳闸状态 */
    if (app_nwk_is_online()) {
        /* 跳闸状态必须到达云端：QOS_1 + 立即发送 */
        app_dp_transmit_report_immediate(TUYA_PRIMARY_ENDPOINT, (UINT8_T *)"\x00", 1,
                                          DP_ID_SWITCH, DP_TYPE_BOOL, QOS_1);
    }
}

app_meter_data_switch_apply();               /* 依据最终状态驱动 GPIO */
```

继电器驱动的最终出口：

```c
VOID_T app_meter_data_switch_apply(VOID_T)
{
    BOOL_T any_alarm = power_alarm_a || ...;
    TUYA_GPIO_LEVEL_E lvl;
    if (any_alarm) {
        lvl = TUYA_GPIO_LEVEL_LOW;           /* 报警期间强制断开（不管 switch_state） */
    } else {
        lvl = switch_state ? HIGH : LOW;
    }
    mo_write(SWITCH_RELAY_PIN, lvl);         /* PC0 */
}
```

这套设计模拟了真实断路器的语义：

| 断路器行为 | 软件对应 |
|-----------|---------|
| 过载跳闸 | 报警 → 继电器断开 |
| 跳闸后保持断开（防自动重合闸伤人） | `switch_state` 锁存 FALSE，必须 App 手动合闸 |
| 跳闸状态掉电保持 | `__meter_rw_save_to_kv` 立即写 KV |
| 故障未排除时不允许合闸 | `switch_apply` 里报警优先于 `switch_state`——用户 App 上点“开”，只要报警还在，继电器就不吸合 |

最后一条是安全设计的关键：**`switch_apply` 的优先级判断让“远程合闸”在报警存在时无效**。用户可以在 App 上把开关拨回 ON（云端 switch_state 变 TRUE），但继电器要等报警解除才真正吸合——和真实断路器的“先排除故障再合闸”一致。

### 3.3 跳闸上报的可靠性设计

跳闸帧用 `app_dp_transmit_report_immediate` + QOS_1，双保险：

- **immediate**：delay_time=0，不排队——报警分秒必争，不能等队列里前面的周期帧发完；
- **QOS_1**：APS 层 ACK + 栈内自动重传——安全关键状态必须到达云端。

离线时的处理也很务实：跳过上报（`if (app_nwk_is_online())`），但 **KV 已经先写了**——本地状态正确，下次入网全量上报会纠正云端。宁可云端晚知道，不可本地状态错。

## 四、阈值修改的联动

阈值本身也是 RW DP（111-113），下发路径和普通 RW 一样，但落地后多了一个动作：

```c
case DP_ID_POWER_SETTING_A:
    if (len >= 4) {
        sg_meter_data.power_setting_a = /* 大端解析 */;
        app_meter_data_update_alarms();    /* ★ 新阈值立即重判报警 */
    }
```

为什么阈值修改要立刻 `update_alarms`？想象用户把阈值从 500W 调低到 100W，而当前功率 200W——不立即重判的话，要等下一个 10 秒采集周期才报警，期间继电器保持闭合，保护就迟了 10 秒。**所有影响安全判定的输入变化，必须立即触发一次重判**，不能等周期。

## 五、出厂自检：产线校准的配套机制

校准和报警要可信，前提是“测量链路本身没坏”。双击触发的电表自检（第 03 篇提过入口）就是这个前提检查：

```c
/* 从 METER_DATA_T 取当前值，与标准值比对 */
#define TEST_STD_VOLTAGE   220    /* V */
#define TEST_STD_VOLTAGE_TOL   15 /* ±15V */
#define TEST_STD_CURRENT    392   /* mA */
#define TEST_STD_CURRENT_TOL    50
#define TEST_STD_POWER     89     /* W */
#define TEST_STD_POWER_TOL    15

/* 三相逐次测：A → B → C，测完 C 后 done（非循环） */
```

自检流程：

```
双击 → 取当前相的 V/I/P
     → |V - 220| ≤ 15 且 |I - 392| ≤ 50 且 |P - 89| ≤ 15 ?
        ├─ 是 → LED 快闪 5 次（app_led_flash_times(5,250,250)）→ 下一相
        └─ 否 → LED 强制熄灭（set_mode_force(OFF)）→ 停在该相
```

设计意图：产线上接标准负载（220V、约 400mA 的阻性负载），双击后看 LED——闪 5 次 = 这一相合格。连续三次双击测完三相。标准值是**固定负载**的期望值（89W ≈ 220V × 0.4A × PF），容差 ±15V/±50mA/±15W 覆盖元件公差。

`TEST_CHANNEL_DONE` 后再次双击被忽略——防止产线工人连击导致状态混乱。恢复出厂（第 08 篇）时 `app_meter_test_reset` 把通道指针拉回 A，为下一轮产测做准备。

## 六、踩坑实录

**坑 1：校准生效但 App 看不到（死区吞掉）。**
前文详解：校准 DP 写入后重置 first-report 标志。

**坑 2：功率报警单位不一致。**
早期版本阈值按 W 比较功率的 W×10 值，200W 负载配上 500W 阈值永远不报警。修复：统一在 `update_alarms` 里做 ×10 对齐。**教训：同一份数据的两个 scale 在同一代码块里混用，就是定时炸弹。**

**坑 3：报警解除后继电器不复位。**
早期版本报警时直接写 `switch_state = FALSE`，报警解除后继电器保持断开——用户没跳闸操作却“被断电”。修复：区分 `switch_state`（用户意图）和 `any_alarm`（物理强制），`switch_apply` 里报警优先但不改写 `switch_state`……等等，看代码——跳闸时确实写了 `switch_state = FALSE`（锁存语义）。那“报警解除后自动恢复”从哪来？没有——本项目选择了**锁存式跳闸**（断路器语义），报警解除后用户必须手动合闸。这是产品决策而非 bug：自动重合闸在故障未排除时有安全风险。**写代码前先把“跳闸后自动恢复还是手动恢复”的产品语义定下来**，否则代码来回改。

**坑 4：阈值边界抖动。**
功率在阈值附近波动时，报警状态高频翻转（继电器咔咔响）。本项目的缓解：功率本身有 ±30W 死区上报（第 08 篇），报警状态变化才上报——翻转频率被采集周期（10s）限死。更严格的场景可加滞回比较器（报警阈值和解除阈值错开 5%），本项目未实现。

## 七、验证方法

1. **校准闭环**：标准源输出 220.0V，设备读 219.2V → App 填电压校准 +8 → 10 秒内设备报 220.0V（±0.1V）；
2. **报警跳闸**：阈值设 100W，接 150W 负载 → 10 秒内继电器断开 + App 开关变 OFF + 报警 DP 114 为 TRUE；负载撤除后报警 DP 变 FALSE 但继电器保持断开（锁存验证）；
3. **报警期间合闸无效**：报警存在时 App 拨开关 ON → 云端显示 ON 但继电器不吸合 → 报警解除后继电器自动吸合（`switch_apply` 优先级验证）；
4. **跳闸掉电保持**：跳闸状态断电重启 → 继电器保持断开，开关 DP 报 FALSE；
5. **产线自检**：接标准负载双击 → LED 闪 5 次；拔掉一相的电流通道再双击 → LED 熄灭。

## 八、小结

- 整机校准用**加性偏移**（7 个 DP 持久化在 KV 0x10，换算后叠加），务实覆盖零点类误差；比例误差是加性方案的边界；
- 校准后重置 first-report 标志，复用既有机制实现“校准效果立即可见”；
- 报警 = 每周期绝对值比较（量纲先对齐 scale）；跳闸 = 报警优先于开关状态 + 状态锁存 + KV 立即持久化 + QOS_1 立即上报——四重保障对应断路器语义；
- 阈值修改立即触发重判，不等周期；
- 双击自检 = 标准负载比对 + LED 语言反馈，产线 30 秒完成三相检验。

功能层面已经完备：能测、能显、能报、能断。最后一件大事是**固件本身如何进化**——下一篇讲 OTA 升级，包括本项目在 OTA 上踩过的所有坑：心跳版本上报、设备类型不匹配、Flash 擦写冲突。
